Questions we hear most

Which SDKs count toward client-side MAU?

Browser SDKs (JavaScript, React and the like), mobile SDKs (iOS, Android, Flutter, React Native), edge SDKs and AI SDKs. Server-side SDKs never add to client-side MAU. They bill as service connections instead, so evaluating millions of users on your backend doesn’t raise this number.

Do page views, sessions or flag evaluations add to the count?

No. A key counts once per month, whether it visits once or a thousand times, and however many flags it evaluates. The number of flags you have doesn’t matter either.

One person on web and mobile, or in several projects: how many MAU?

One, as long as you use the same key everywhere. The same key in several environments or projects also counts once. A different key for the same person, such as a device ID on mobile and a user ID on web, counts twice.

We send user, device and organization contexts. Are we billed for all of them?

No. You’re billed on one context kind, the one with the most unique keys that month, which is usually user. The other kinds in a multi-context ride along for free. Watch for one thing: if another kind has more keys, such as device IDs for anonymous traffic, that kind becomes the one you’re billed on.

Do anonymous visitors count?

Yes. The SDK makes up a key for an anonymous visitor and saves it on the device, so a returning visitor counts once. A private window, cleared browser storage or a fresh app install gets a new key, and a new MAU. When an anonymous visitor signs in, their anonymous key and their user key are both counted that month.

Why is our MAU higher than our analytics numbers?

This is the most common surprise, and the causes are usually the same: bots and crawlers, headless browsers in automated tests, code that makes a new key on every page load, device IDs used as keys, and anonymous traffic on pages that don’t use flags. The Usage page breaks MAU down by SDK, app and anonymous traffic, which usually points to the source.

How do we bring it down?

Keep keys stable across visits and devices. Don’t start the SDK for traffic you never target, such as bots or pages without flags. Keep automated test browsers out of production environments. None of this changes how your flags behave for real users.

When does the count reset?

At the start of each billing month. Everyone who comes back in the new month counts again, once.

What happens if we go over our plan?

Your flags keep working. LaunchDarkly never throttles or turns off flags for going over. On self-serve plans the overage is billed the following month. On Enterprise contracts, the contract is adjusted only when usage stays over your commitment; your account team will walk through it with you.

Where can we see our usage?

In LaunchDarkly, go to Account settings, then Usage, then Client-side MAU. You can break it down by project, environment, SDK, app and anonymous traffic, and see month to date or a rolling 30 days.

Questions we hear most

Which SDKs bill as service connections?

Server-side SDKs, the ones that run in your backend: Node.js, Java, Go, Python, .NET, Ruby, PHP, Rust and the rest. Browser, mobile and edge SDKs bill on client-side MAU instead. Contexts your backend evaluates never add to client-side MAU.

What exactly is one service connection?

One instance of one server-side SDK, connected to one LaunchDarkly environment, for one full month. Shorter periods count as a fraction: two instances connected for half the month each add up to one.

Is it per pod, per worker, per region or per SDK key?

Per running SDK instance, per environment. Every pod, replica or container that starts its own SDK counts, in every region. This example assumes workers share one SDK instance ID and count once; workers with separate SDK instance IDs count separately. Use the process lifecycle supported by your SDK. An SDK key isn’t a unit: ten pods using one key are ten connections. One instance connected to two environments counts twice.

Are we billed on our peak number of pods?

No. You’re billed on total connected time across the month. Autoscaling up to 100 pods for an afternoon adds only that afternoon, not 100 connections.

Does the Relay Proxy reduce our bill?

No. This is the most common misunderstanding. The Relay Proxy reduces the network connections leaving your infrastructure, not billed service connections. Every SDK connected to the Relay Proxy still counts. The Relay Proxy’s own connection to LaunchDarkly isn’t billed, so adding one doesn’t raise the bill either. Use it for resilience, network control and fewer outbound connections, not for cost.

Do dev, staging and preview environments count?

Yes, the same as production. Local dev servers, PR preview apps and test runs that start the SDK all add connected time. If non-production usage is large, raise it with your account team.

How do serverless functions like AWS Lambda count?

By the time the function is running with the SDK, not by invocations. A million one-second invocations add up to a small fraction of one service connection. To estimate, multiply your average run time by your number of invocations.

Why did our count suddenly spike?

Most often, code creates a new SDK client per request or in a loop instead of once at startup. Other causes are new deployments or replicas, forked worker processes that each start an SDK, and dev or preview apps. Give each app an application ID in its SDK configuration, and the Usage page will show which app is responsible.

Is polling a way to save?

Polling is not currently billed. Proposed ASI aims to count how long an SDK is active, whether it streams or polls. In that example, changing the interval changes how quickly flags update, not the count.

How is PHP counted?

PHP starts a new process for every request, so it can’t hold a stream open, and each request polls for flags. This example counts each poll as 30 seconds. Polling is not currently billed. In Proposed ASI, the PHP example keeps that rule provisionally. A flag with prerequisites can make more than one poll. Caching flag data between requests means fewer polls.

We run Kubernetes or multi-process apps. Is there different pricing?

Some Enterprise contracts price these connections at a different rate. The count works the same way: every pod and process that starts an SDK still counts. Only the price per connection differs.

What about daemon mode or the Relay Proxy’s offline mode?

Billing for these setups is set in your contract. Talk to your account team before you design around them.

How do we estimate what we’ll use?

For each app, multiply the number of instances that run the SDK by the number of environments they connect to, and by the share of the month they’re up. Add the apps together. Always-on services dominate the total; short bursts barely move it.

What happens if we go over, and where do we see usage?

Your flags keep working; LaunchDarkly never throttles for going over. Self-serve plans pay the overage the following month, and Enterprise contracts adjust only when usage stays over your commitment. To see usage, go to Account settings, then Usage, then Service connections. You can break it down by environment, SDK, app and Relay Proxy version.
